## Anomalies

- **N1 `clients` over-reports by the number of ESP-NOW peers.** `/state.clients` and `w`'s `apClients` read `2` with exactly one station (the box) associated, and **`1` with the box disconnected** (`wpa_cli disconnect`, 6 s later `w`: `apClients=1`; reconnect → `2`). `WiFi.softAPgetStationNum()` → `esp_wifi_ap_get_sta_list()` includes ESP-NOW peers registered on the AP interface (the node `78:E3:6D:19:18:38`). Cosmetic in the UI ("clients" badge), but it also means the hub's `max_conn=2` may need checking with two phones at once (not tested here — see phone checklist).
- **N2 Unicast IDENTIFY intermittently lost** — see D1.
- **N3 One failed `/state` in 150 during the soak** (23:46:49; the Python JSON parser got an empty/truncated body within `curl -m3`). Not reproduced in 250 immediate follow-up polls. Hub `minHeap` reached 160 616 at some point during the soak (vs 165 668 after B9), i.e. a ≈ 5 kB transient dip; cannot be tied to the failed request from the logs. Possibly a Wi-Fi retry on the box side. Worth a longer soak with per-request status logging before Phase 2.
- **N4 `briEff` formula.** Implementation uses `briEff = bri × cap / 100` (review disposition S3-22), not `min(bri, cap)` as written in the review's R1 sketch. Visible in B4: white at `bri 50` → `briEff 30` (min() would give 50). Both give the brief's 60 at `bri 100`. Deterministic and arguably the more sensible curve; documented, not a defect.
- **N5 `/state` shape extras**: `state.hubState` and `self:false` on non-self rows (§4 has neither). Harmless for the page.
- **N6 Hub reboot while the page is open**: after the hub reset in B6 the hub logged `[WEB] GET /chrome-variations/seed -> 302 /` — a background process on the box hit the portal because its DNS was hijacked (see Environment). Not a firmware issue, but a reminder that the captive DNS answers *every* name, so a phone that stays associated will see every app's traffic redirected to the sign.
- **N7 `arduino-cli upload` unusable on this box** (baud switch fails); esptool at 115200 works. Record for the owner's Windows setup: if the same adapters are used, set `UploadSpeed=115200`.
- **N8 `wlp4s0` is 60 GHz** (wil6210); the brief's instruction to use it cannot work. Use `wlp3s0`.

## Defects for fix agent

**D1 — Unicast IDENTIFY (and therefore FORGET) is fire-and-forget; 2 of 11 identifies never reached the node.**
- Where: `hub.cpp:321` `radio::send(mac, &id, sizeof(id), false);` in `identifyPos()`; `forgetPos()` sends FORGET the same way (one attempt, `needsAck=false`). `radio::send` with `needsAck=false` frees the slot after a single `esp_now_send` (and on immediate failure, `radio_espnow.cpp:244-251`, counts `txFail` and drops it).
- Repro: with the node RUNNING at pos 2, `curl -s -X POST http://192.168.4.1/cmd -d '{"cmd":"identify","pos":2,"ms":800}'` repeatedly with 2 s gaps while capturing node serial. Observed: hub always logs `[HUB] IDENTIFY pos 2 (…) 800 ms`, reply `ok:true`; node logged `[NODE] IDENTIFY 800 ms` for 9 of 11; the misses were the first command of a batch at 23:37:44.6 and 23:38:45.2 (hub `txFail` 0 → 1 over the session, so at least one loss was over-the-air rather than an `esp_now_send` error). Broadcast (`pos 255`) never missed.
- Impact: Identify is cosmetic, but a lost **FORGET** leaves the node with its NVS position while the hub has dropped the row; on the node's next boot it re-HELLOs with that pos and the hub re-accepts it — the forget is silently undone (exactly the case S3-25 warned about).
- Suggested fix: send IDENTIFY and FORGET with `needsAck=true` (the ACK/retry path already exists for ASSIGN), or at minimum repeat FORGET ×3 like RESETORD. Verify with the repro above (expect 20/20) and with `forget` → power-cycle node → node must boot `NVS pos=0`.

**D2 — `clients` counts ESP-NOW peers (N1).** `hub::buildState` (`hub.cpp:389`) and `transport_web::apClients()` use `WiFi.softAPgetStationNum()`. Suggested: filter `esp_wifi_ap_get_sta_list()` entries against the hub table MACs (or count only entries with a DHCP lease via `tcpip_adapter`/`esp_netif` station list), and report `clients = stations − peers_in_table`. Repro: one box associated → `/state.clients` is 2; disconnect it → `w` shows `apClients=1`.

No blocking defects: B1–B10 all pass on the hardware; D1 is the only behavioural issue and it is a reliability gap, not a functional failure.

## Phone checklist for the owner (cannot be automated)

Power both boards (hub shows `H`, node `I`, green). Join Wi-Fi **LEDSIGN-HUB / sign1234**.

**iOS (Safari captive-portal sheet)**
1. After joining, the "Log In" captive sheet should pop within ~5 s showing the sign page (dark theme, four tabs). If it does not, open Safari → `http://192.168.4.1/`.
2. Message tab: type `HI {heart}` using the keypad for the heart; char-count reads `3 / 2` in red (over by one); Send → boards show `H`, heart; textarea keeps your text after the next poll.
3. Look tab: tap red swatch → both boards red within ~0.1 s; brightness slider to 50 → label `50%`; white swatch → label shows `(effective 30%)`; slider to 100 → `(effective 60%)`; rainbow swatch → hues cycle on both boards **in step**; Blink → both boards blink **in phase** at 500 ms; speed slider 2000 → slow blink; Static.
4. Boards tab: two cards, pos 1 badge `HUB`, pos 2 online with RSSI/age; tap Identify on pos 2 → node flashes (if it does not, tap again — see D1); Identify all → both; power off the node → card goes offline within 10 s and a **Forget** button appears; Reset order → confirm dialog → pos 2 card disappears; press the node's claim key / `c` → card returns.
5. Settings tab: SSID `LEDSIGN-HUB`, fw 1, heap ≈ 175 kB, clients (expect 2 with one phone — N1), uptime ticking; console `{"cmd":"get"}` → reply log shows the JSON.
6. Leave the sheet open 2 min: no "cannot connect" errors, page keeps polling. Then tap "Done" and reopen from Safari — page loads (not cached stale: `no-store`).

**Android (Chrome, "Sign in to network" notification)**
1. Join → notification "Sign in to LEDSIGN-HUB" within ~10 s → tap → the page opens in the captive webview. Fallback: Chrome → `http://192.168.4.1/`.
2. Repeat items 2–5 above. Specifically check: symbol keypad glyphs render (`:)`, `:(` not emoji), sliders respond to touch without the 300 ms delay, `<input type=color>` opens the system picker and applies on close, `confirm()` dialogs work inside the webview, toast appears on an error (type `{"cmd":"bogus"}` in the console).
3. Keep the phone associated for 5 min with the page in the foreground — page must keep updating and the phone's other apps must *not* think it has internet (expected: Android shows "no internet" and may ask to stay connected — say yes).
4. **Two phones at once** (max_conn = 2, but N1 means the AP may think one slot is taken): confirm the second phone can associate and load the page; note the result for D2.
