# Verification — Phase 4 (hub-hosted OTA) on hardware

Spec: `docs/build-briefs/PHASE4_OTA_hub_hosted_updates.md` O1–O10 as amended by `docs/reviews/PHASE4_REVIEW.md` (IDF rollback + `verifyRollbackLater()`, one-reset rollback, `PROTO_VER` 1, `MAX_FRAME` 128) and its "Refactor disposition" / "Interpretations for the verifier". Run 2026-11-09 13:23–13:58 (box clock; all serial lines are wall-clock timestamped on the same clock as `curl`).

## Verdict

**O1, O2, O3, O5, O6, O7, O8, O9, O10 PASS. O4 PASS only with a workaround: FAIL as specified (D1).** The documented flow is "upload to the hub, then Update all boards". Every hub upload reboots the hub. After that reboot the hub cannot send any unicast to a node until the node reboots by itself (D1). So `ota_nodes` straight after a hub OTA always fails `no response` (3/3 attempts). After a node reset, which makes it re-HELLO, node OTA works every time: 4/4 runs, 23–24 s per node, with 0 % OTA_STATUS loss over the complete runs. Rollback works exactly as reworded: a truncated image is refused with no reboot, and one reset inside the 30 s window returns the hub to the previous slot (`state ABORTED`). Both boards end on the same committed build `387ea87` / buildId `bfc0e847`, slot `app1`, valid, showing "GO TEAM", green, words mode, wspeed 2000.

## Anomalies / observations

1. **D1 below.** This is the only defect that breaks an acceptance flow.
2. **The hub upload stalls the hub's own word timing.** During a 12 s `/ota` upload the hub's `apply` lines run up to ≈ 180 ms late (e.g. `advance … applyAt=+285` at 18.355, but `apply` at 18.820), and node and hub word switches drift apart by up to ≈ 160 ms (seq 228: hub 18.820, node 18.663). One node apply landed at `(-82 ms)` and the next at `+529 ms`. The display effect lasts only for the upload, and the review notes that the port-80 server blocks for the transfer. The node download (port 8080 task) does **not** cause this (± 11 ms).
3. **A refused upload still reads the whole body.** `POST /ota` while a node OTA was running took 5 s to answer, so the hub received all 1.1 MB before saying `node update in progress`. In that window the node's 20 % status reached the hub ≈ 0.9 s late. This is harmless.
4. **No fast failure when the in-flight node comes back on its old image.** In O6a the node re-HELLO'd with the old buildId 6 s after its reset, but the hub kept the row `updating 30 %` until the 120 s timeout. A HELLO/HB from the in-flight MAC that carries a buildId ≠ target could fail it immediately (`node rebooted (old image)`). This is an enhancement, not an acceptance failure.
5. **A rebuild of the same commit gives a different buildId.** A `--clean` rebuild of `387ea87` differs from the release `.bin` from byte 177, inside `esp_app_desc`, because of the build time and date. Since buildId = `app_elf_sha256[0..3]`, rebuilding the same commit and uploading it would make every node "need an update". This is expected with an ELF-hash id. It is only a concern if releases are ever rebuilt.
6. Node `s` prints `imageLen=0` (only the hub measures the image). This is cosmetic.
7. Hub `minHeap` dropped to 125 392 B during the truncated upload, and was 139 492 B during the final session. It was never close to trouble.
8. `/state.clients` = 1 with only the box associated. Step-3 N1/D2 (peers counted as clients) appears fixed or unchanged; it was not re-tested in depth.

## Defects for fix agent

**D1 (blocking for O4 as specified): after a hub reboot the hub has no ESP-NOW peer entry for known nodes, so every unicast to them fails until each node reboots.**

- **Mechanism:** `hub.cpp` calls `radio::addPeer(mac)` only in `onHello()` (line 286). When the hub reboots (every hub OTA, also power cycles), it reloads the table from NVS but registers no peers. A node that was RUNNING sees `hub clock went backwards: hub restarted, resyncing` and goes `LOST_HUB -> RUNNING` from SHOW alone. It never sends HELLO, so the hub never re-adds it. After that, every `radio::send(nodeMac, …, needsAck)` fails: OTA_ENTER, IDENTIFY, SETMIRROR, SETPOS, FORGET. The hub logs `[RADIO] give up <mac> type=N … after 5 tries` within ≈ 1 s and `txFail` rises by about 5–6 per command. The node logs nothing. `esp_now_send` to an unregistered peer returns `ESP_ERR_ESPNOW_NOT_FOUND` at once, which explains the 1 s give-up. The bug is latent since Step 1, but Phase 4 makes it certain: the documented flow (upload → hub reboots → "Update all boards") fails `no response` on every node, every time.
- **Repro:** hub and node RUNNING. `curl -F file=@<any differing .bin> http://192.168.4.1/ota`, wait for the hub to reach RUNNING (the node resyncs without a reset), then `curl -d '{"cmd":"ota_nodes"}' http://192.168.4.1/cmd`. Hub: `OTA_ENTER pos 2 …` → `give up 78:E3:6D:19:18:38 type=14 … after 5 tries` → 10 s later `pos 2 failed: no response`. `{"cmd":"identify","pos":2,"ms":800}` also gives `give up … type=8`. Reset the node (it HELLOs, hub `addPeer … OK`) and both work. Observed 3/3 for OTA_ENTER (13:33:44, 13:35:54, 13:41:23) and 4/4 for IDENTIFY.
- **Suggested fix (any one):**
  - (a) In `hub::begin()` after the table load, `radio::addPeer()` every table MAC.
  - (b) In the HB handler (`hub.cpp` around line 610), `radio::addPeer(srcMac)` when the srcPos/MAC is in the table. `addPeer` is idempotent through `esp_now_is_peer_exist`.
  - (c) In `radio::send()`, add a missing unicast peer before queueing.

  (a)+(b) is the most robust. Also log the `esp_err_t` when `esp_now_send` fails immediately, so this shows as "peer not found" rather than as an ACK timeout.
- **Re-verify:** O3 then O4 back to back with no node reset. Also `identify pos 2` right after any hub reboot.

**D2 (minor, enhancement): the in-flight node that rejoins on its old image is only failed by the 120 s timeout.** See anomaly 4. Fail the row as soon as a HELLO/HB from `otaRec[cur]`'s MAC carries a buildId ≠ target, after OTA_ENTER was ACKed.

**D3 (minor): the hub upload delays the hub's own sequencer by up to ≈ 180 ms during the 12 s transfer** (anomaly 2). Consider calling the sequencer tick (not only `radio::pump()`) between upload chunks, or accept it and document it.
