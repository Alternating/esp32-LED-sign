# Build brief — Phase 4 (pulled forward): hub-hosted OTA for all boards

Owner decision 2026-11-08: with 10 boards, wired reflashing is the bottleneck. The hub must host firmware updates for every board. Battery telemetry is dropped from scope (fields stay in the protocol as zeros; UI stops showing mV).

Builds on verified Phase 1 (`docs/reviews/STEP{1,3,2}_VERIFICATION.md`). Plan reference: `docs/PROJECT_PLAN.md` §7 Phase 4, §2.3 (channel pinning: a node joining the hub's AP stays on channel 6, so ESP-NOW is unaffected).

## Core design (settled)
- **One binary** for hub and nodes (as today). The hub serves **its own running app image** (`esp_ota_get_running_partition()` → `esp_partition_read` streamed over HTTP) — no separate storage needed. "Update all boards" = make every node run what the hub runs.
- **Partition scheme changes to `min_spiffs`** (two 1.9 MB OTA app slots + 190 kB SPIFFS; LOLIN32 FQBN `PartitionScheme=min_spiffs`). This requires one final wired full install of every board (new HUB/NODE install images). `LED_Sign_update_app.bin` remains for wired updates but must then be written to the **running slot's address** — simpler: the flasher's `--update` mode is retired in favour of OTA; wired = full install only. Document this.
- **Build identity**: `esp_app_get_description()->app_elf_sha256` (first 8 hex chars = `buildId`) plus `esp_app_get_description()->version` set to a build string. Set the version via `-DAPP_VERSION="\"<git short hash>\""` is awkward in Arduino IDE; instead `config.h` gets `#define FW_VERSION_STR "0.4.0"` bumped by hand AND `tools/make_images.sh` writes `firmware/LED_Sign_Mesh/build_id.h` with `#define BUILD_GIT "<short hash>"` before compiling (gitignored). Nodes report `buildId` (4 bytes, from the ELF sha) in HELLO and HB; hub compares to its own. Equal → up to date.
- **Hub update (from phone)**: Settings → Firmware: file picker + "Upload to hub" → `POST /ota` multipart (`WebServer::upload()` + `Update.begin(UPDATE_SIZE_UNKNOWN)` / `Update.write` / `Update.end(true)`), progress %, then hub reboots into the new slot. Rollback safety: `esp_ota_mark_app_valid_cancel_rollback()` after the hub has been RUNNING for 30 s with the AP up; otherwise the bootloader rolls back (needs `CONFIG_BOOTLOADER_APP_ROLLBACK_ENABLE` — check whether the Arduino core enables it; if not, implement our own: write `pendingVerify=1` to NVS before reboot, clear after 30 s healthy, and on boot with `pendingVerify` still set 3 times → `esp_ota_set_boot_partition(other)`).
- **Node update (hub-driven, one at a time)**: `POST /cmd {"cmd":"ota_nodes"}` (or per board `{"cmd":"ota_node","pos":N}`) → hub builds a queue of online nodes whose `buildId != mine`, processes sequentially: unicast `OTA_ENTER{ssid, pass, hubIp, port, buildId}` (new msg type 14, needsAck) → node: shows OTA pattern (position digit in **blue**, with a progress bar filling the bottom 2 rows), stops HELLO/HB, `WiFi.begin(ssid,pass)` on the SAME channel (do NOT change channel; `WiFi.setAutoReconnect(false)`), `HTTPClient GET http://192.168.4.1/fw.bin`, `Update.begin(contentLength)`, `Update.writeStream`, `Update.end(true)`, reports `OTA_STATUS{pct, state}` every 5 % and on finish/fail (unicast to hub via ESP-NOW — ESP-NOW keeps working while associated on the same channel; if it proves unreliable while associated, report via `POST /ota_status` over HTTP instead — pick ONE after bench test and document), reboots on success → DISCOVER → hub sees new buildId in HELLO → next node. Timeout per node 120 s → mark failed, continue. Node failure path: `Update.abort()`, `WiFi.disconnect()`, back to mesh with the old firmware (slot untouched since Update only commits on `end(true)`).
- **AP capacity**: `softAP(..., max_conn=4)` (2 phones + 1 updating node + spare). Hub `/fw.bin` is a single-client stream; `/state` keeps working during OTA (the WebServer is single-threaded: chunk the fw stream in 4 kB writes and call `server.handleClient()`? No — `WebServer` cannot interleave. Instead serve `/fw.bin` from a **dedicated task** using a raw `WiFiServer` on port **8080** (so the phone UI on port 80 stays responsive): `OTA_ENTER` carries port 8080. Streaming 1.1 MB at ~300–600 kB/s ≈ 2–4 s per node + 10 s reboot/rejoin.)
- **UI** (Settings → Firmware section): hub buildId/version/slot; file upload with progress; "Update all boards" button → list of boards with `buildId`, status (`up-to-date`, `queued`, `updating 42 %`, `rebooting`, `done`, `failed: <reason>`), from `/state.ota` polled every 2 s; per-board "Update" button. Boards tab shows a small `fw` badge (short buildId), red if ≠ hub.
- **Remove battery UI**: drop `mV` from cards; keep `mv` JSON field (0) for compatibility this step; `battery.h` stub stays.
- Serial: hub `o` = ota_nodes, `O<pos>` = ota one node, `s` shows buildId/version/slot and OTA queue; node `s` shows buildId/slot.

## Scope
1. `config.h`: `FW_VERSION_STR`, `OTA_PORT 8080`, `OTA_NODE_TIMEOUT_MS 120000`, `OTA_VERIFY_MS 30000`; `AP max_conn 4`.
2. `protocol.h`: `OTA_ENTER=14 {Hdr; char ssid[33]; char pass[33]; uint32_t ip; uint16_t port; uint8_t buildId[4]; uint32_t size;}`, `OTA_STATUS=15 {Hdr; uint8_t pct; uint8_t state; uint8_t buildId[4]; char msg[24];}`; `Hello`/`Hb` gain `uint8_t buildId[4]` (bump `PROTO_VER` to 2; hub accepts v1 frames from not-yet-updated nodes by length so the first OTA rollout works: treat missing buildId as 00000000 = "unknown → update").
3. `ota.h/.cpp` (both roles): `buildId()`, `fwServerTask` (hub, port 8080, streams running partition), `hubReceiveUpload` hooks for `/ota`, `nodeRunOta(const OtaEnter&)` state machine with progress callback, `markHealthyOrRollback()`.
4. `hub.cpp`: OTA queue/state machine in `tick()`, `OTA_STATUS` handling, `BoardInfo.buildId/otaState/otaPct`, `/state.ota {hub:{buildId,version,slot,pendingVerify}, queue:[...], current:{pos,pct,state}}`, `buildState` per-board `fw`.
5. `node.cpp`: `OTA_ENTER` handler → `NodeState::OTA` (render blue digit + progress rows; no HELLO/HB; LOST_HUB timer suspended), reboot on success, fallback on failure.
6. `transport_web.cpp`: `POST /ota` multipart upload → Update → reply JSON → reboot after 1 s; `GET /ota` status; keep `/fw.bin` OFF port 80.
7. `commands.cpp`: `ota_nodes`, `ota_node {pos}`, `ota_cancel`; `get`/`state` carry ota info.
8. `web/index.html`: Firmware section; fw badges; remove mV; ≤ 44 kB.
9. `tools/make_images.sh`: `min_spiffs` FQBN; writes `build_id.h`; outputs HUB/NODE **install** images (merged, 0x0) + `LED_Sign_ota.bin` (= the app `.bin`, what you upload to the hub). `tools/flasher.py`: drop `--update`, add note that updates are OTA; `tools/flash_board.sh` likewise. `firmware/bench/README.md` + `README.md`: new FQBN, flow "wired install once → OTA forever".
10. Rollback: verified behaviour documented (either IDF rollback or our NVS-based scheme).

## Out of scope
Battery ADC, order/swap, BLE, signed firmware, OTA from the internet.

## Acceptance (verification agent, Qwen box; hub 9C:9C:1F:E3:CE:54 + node 78:E3:6D:19:09:B0 (board 5, pos 5) or any node on USB; the box joins `LEDSIGN-HUB` from wlp3s0 as in STEP3)
- O1 Build with `PartitionScheme=min_spiffs`: 0 errors/0 warnings; app ≤ 1.5 MB; `make_images.sh` produces HUB/NODE install + `LED_Sign_ota.bin`; `build_id.h` matches `git rev-parse --short HEAD`.
- O2 Wired install (last time): HUB image → hub (role HUB, table/sign are wiped — record and re-enter text "GO TEAM" afterwards), NODE image → node. Both boot; `s` shows buildId/version/slot `app0`.
- O3 Hub OTA from the box: `curl -F "file=@LED_Sign_ota.bin" http://192.168.4.1/ota` with a **rebuilt** image (change `FW_VERSION_STR` to make the buildId differ) → progress on serial, reboot into `app1`, `s` shows new buildId, AP + table + sign intact (NVS untouched), node still RUNNING within 10 s.
- O4 Node OTA: `{"cmd":"ota_nodes"}` → hub log `OTA queue: pos 5 (buildId old)`, node log `OTA_ENTER → joining LEDSIGN-HUB → GET /fw.bin 1081xxx B → 10 %…100 % → Update OK → reboot`; node rejoins as pos 5 with the hub's buildId; `/state.ota` shows done; total time per node recorded (target < 40 s).
- O5 Up-to-date path: `ota_nodes` again → queue empty, node untouched.
- O6 Failure paths: (a) power-cycle the node at ~50 % → hub times out/marks failed after ≤ 120 s, node boots the OLD firmware (slot untouched) and rejoins; (b) `ota_cancel` mid-transfer.
- O7 Rollback: flash the hub via `/ota` with a deliberately broken image (e.g. the `.bin` with 1 kB truncated → `Update.end` fails → reported, no reboot); and simulate a bad-but-valid image by a build with `#define OTA_SELFTEST_FAIL` that reboots before marking healthy → after 3 boots the hub is back on the previous slot (document whichever rollback mechanism was implemented).
- O8 Phone UI (Playwright stub): Firmware section renders, upload control posts multipart, "Update all" posts `ota_nodes`, board list shows statuses from a stub `/state.ota`; fw badge red when ≠ hub. Screenshot `docs/reviews/phase4_ui_firmware.png`.
- O9 Regression: A3/A5, identify (steady 10 s), mirror flip, sequencing C4 (1000 ms ± 50), 5-min soak with the box's phone-emulation polling `/state` every 2 s.
- O10 ESP-NOW during node association: measure hub→node Show delivery while the node is associated (before it starts the download): if `OTA_STATUS` over ESP-NOW loses > 10 %, switch status reporting to HTTP and document.
